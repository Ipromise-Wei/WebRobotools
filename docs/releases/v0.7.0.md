# v0.7.0 版本说明

发布日期：2026-09-28

这是一次面向真机导航卡顿的通信架构升级。目标是让视频、地图和路径的显示流无法再占用 Nav2 的控制时序。

## 工控机本地控制，Web 端轻量显示

新增工控机侧 `telemetry_relay.py`，由“手动建图”和“自动建图”方案自动启动。

- 中继在工控机本地订阅原始 `/map` 与 `/plan`；原始 OccupancyGrid 和完整 Nav2 路径不再跨 Web 服务器与工控机之间的 DDS 网络。
- 中继只发布 `/webrobot/web_map`（最多 65,536 栅格、最多每秒一次）和 `/webrobot/web_plan`（最多 256 点、最多每 0.5 秒一次）。两个显示 Topic 使用 `BEST_EFFORT + VOLATILE + depth=1`，旧帧可丢弃而不会重传或排队。
- Web 地图仍按原有 REST/WebSocket 方式显示。点击的世界坐标会作为小型 JSON 消息发送到中继；中继使用原始本地地图进行范围、坐标系、原点和空闲栅格校验，然后在本机向 `/navigate_to_pose` 发出 Action 请求。
- 目标、取消、状态与控制租约带唯一请求标识。即使不同 DDS Topic 上的消息抵达顺序不同，提前抵达的取消也会形成短时取消标记，不能让迟到的目标启动；来自旧 Web 进程的状态或租约也不能影响新目标。

## 导航与视频低延迟

- 工控机速度看门狗不再以跨网络的快速心跳决定 Nav2 速度，而是依据本地 `/navigate_to_pose/_action/status` 和本地 `/webrobot/nav_cmd_vel`。Nav2 的本地速度超过 0.5 秒未更新时，仍持续输出零速度。
- Web 后端设置目标前不再同步 SSH 查询运行模块状态。它只检查新鲜的里程计、`map → base_link`、工控机看门狗、显示地图和本地中继/Nav2 就绪信号，因此 HTTP 请求会快速返回“发送中”。
- Web 服务对执行中的目标保持请求关联的低频控制租约。正常取消或关停会立即发送取消；若 Web 服务真正消失，工控机中继在 10 秒后请求取消无人监管的目标。此租约不参与每个速度周期，避免短暂网络波动导致机器人反复走停。
- 工控机 RealSense 预览默认调整为 `1280×720@12fps`、JPEG 质量 70；FFmpeg 禁用缓冲，服务端在一次读取中只保留最新完整 JPEG，并丢弃超过 800 KB 的显示帧。

## 升级与验证

升级后必须通过 Web 页面先“停止建图/全部停止”，再重新启动手动或自动建图方案。这样后端才会将新的 `telemetry_relay.py`、速度看门狗和底盘运行脚本部署到工控机，并按新依赖顺序启动“工控机实时通信中继”。仅重启浏览器或只重启 Nav2 不足以应用本版控制链路。

建议在清空的安全区域验证：

1. 模块面板应显示“工控机实时通信中继”和“Nav2 导航”均为运行中；
2. 打开视频和地图后设置目标，机器人应连续运动，视频应显示最新画面而非回放积压帧；
3. 点击“取消导航”后确认导航状态变为已取消；准备好现场物理急停再进行任何移动测试。

已完成 Python 语法编译、Shell 语法检查、地图/目标关联回归用例补充，以及前端 TypeScript 生产构建。本开发机的系统 Python 为 3.9，而 ROS 2 Humble 后端需要 Python 3.10；请在部署服务器的 ROS 虚拟环境中执行完整回归：

```bash
cd ~/WebProjects/WebRobotools/backend
./.venv-ros2/bin/pip install -r requirements-dev.txt
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv-ros2/bin/pytest
```

## 安全与边界

本版消除了已知的应用层带宽竞争，但以太网、交换机、DDS 实现和浏览器本身并不能保证数学意义上的“零延迟”。若仍有明显卡顿，应在现场记录 `/webrobot/nav_cmd_vel`、`/cmd_vel`、CPU、网卡错误和相机实际帧大小，再判断是否需要为控制流设置独立 VLAN/NIC 或系统级 QoS。

Web 停止、10 秒控制租约和 0.5 秒本地速度超时都不替代物理急停。真机调试必须始终保留人员监护和可触达的硬件急停。
